## 1. Repository setup

Your app must live in a **public GitHub repository** under the `Mooroon5-CNP` org (or any org the GitHub App CNP is installed on).

> **The repository must be public.** Organization-level Actions variables (`WIF_PROVIDER`, `GCP_SA_EMAIL`, `REGISTRY_URL`) are only accessible to public repositories. A private repo will silently receive empty values for these variables, causing the GCP auth step to fail with: *"must specify exactly one of workload_identity_provider or credentials_json"*.

Minimum file tree:

```
my-app/
├── .github/
│   └── workflows/
│       └── ci.yml          ← generated by the portal on onboarding
├── src/
│   ├── index.js            ← entrypoint
│   └── index.test.js       ← at least the /healthz and /ready tests
├── Dockerfile
├── package.json
└── .eslintrc.json          ← required for the lint step
```

The `ci.yml` is **auto-generated by the portal** when you create a deployment. You do not write it yourself — see [§4](#4-ci-pipeline).

## 2. Dockerfile contract

The CI pipeline runs **hadolint** on your Dockerfile. Violations fail the build.

### Required pattern (multi-stage, Node 20 Alpine)

```dockerfile
FROM node:20-alpine AS deps
WORKDIR /app
# hadolint ignore=DL3018
RUN apk add --no-cache python3 make g++   # only if native addons needed
COPY package*.json ./
RUN npm ci --omit=dev

FROM node:20-alpine
# hadolint ignore=DL3018
RUN apk add --no-cache tini
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY src/ ./src/
EXPOSE 8080
USER 1000
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["node", "src/index.js"]
```

### Rules enforced by hadolint

| Rule | Requirement |
|------|-------------|
| Base image | **Always** `node:20-alpine` — no other tags, no `latest` |
| Non-root user | **`USER 1000`** (numeric UID) — **not** `USER node`. Numeric UIDs are portable across base images. Using `USER node` will still work locally but fails Hadolint DL3002 checks in stricter CI configs. |
| Port | **`EXPOSE 8080`** — must match `appPort` set in the portal |
| Init process | Use `tini` (`apk add --no-cache tini` + `ENTRYPOINT ["/sbin/tini", "--"]`) to handle PID 1 signal forwarding and zombie reaping |
| No `apt-get` / `yum` | Alpine only — use `apk` |
| Multi-stage build | Required — keeps the final image small and free of build tools |
| `/tmp` write dir | If your app writes to `/tmp` at runtime, nothing to add. If you need persistent data, use `/data` with a GCS volume (see §5). |

### Why `USER 1000` not `USER node`?

```dockerfile
# WRONG — fails Hadolint DL3002 and is brittle across base images
USER node

# CORRECT — numeric UID, portable, matches what the platform expects
USER 1000
```

The `node` user has UID 1000 in `node:20-alpine`, but relying on the name is fragile: if the base image ever changes the UID mapping, your app silently runs as the wrong user. Always use the numeric UID.

## 3. Health probes

The platform's ingress and Cloud Run readiness checks call two fixed endpoints. Both **must** respond with HTTP 200.

```
GET /healthz  →  200 { "status": "ok" }
GET /ready    →  200 { "status": "ready" }
```

Minimal Express implementation:

```javascript
app.get('/healthz', (_req, res) => res.json({ status: 'ok' }));
app.get('/ready',   (_req, res) => res.json({ status: 'ready' }));
```

Cloud Run will **refuse to serve traffic** until `/ready` returns 200. If your app takes time to initialize (e.g. DB migration on startup), make `/ready` return 503 until the DB is ready, then 200.

## 4. CI pipeline

### How it works

When you onboard via the portal, the portal:
1. Forks/commits a `ci.yml` into your repository's `.github/workflows/`
2. Creates the Crossplane `cloudrun-claim.yaml` in `config-repo/apps/{appName}/crossplane/`
3. Creates the Kustomize overlays in `config-repo/apps/{appName}/overlays/dev/` and `prod/`
4. ArgoCD applies the Crossplane claim → Cloud Run service is provisioned

On every subsequent push to `main`, CI:
1. Runs **lint** (ESLint + Hadolint)
2. Runs **tests** (`npm test`)
3. Scans for **secrets** (Gitleaks)
4. Scans **npm deps** for CVEs
5. **Builds and pushes** the Docker image to GCP Artifact Registry (`europe-west9-docker.pkg.dev/cnp-terraform-500015/cnp-registry/{appName}:{sha}`)
6. **Updates** `config-repo/apps/{appName}/crossplane/cloudrun-claim.yaml` with the new image SHA → ArgoCD syncs → Cloud Run updates


### Required secret

Your GitHub repository must have a secret named **`CONFIG_REPO_TOKEN`** — a GitHub PAT with `repo` scope on `Mooroon5-CNP/config-repo`. The portal admin adds this when onboarding automatically, if it fails to do so please ask your manager or devOps to instert it.

## 5. Persistent storage (SQLite on GCS)

By default, Cloud Run containers are **ephemeral** — anything written to the local filesystem is lost when the instance restarts or scales.

If your app needs a persistent database (SQLite, uploaded files, etc.), enable **"DB persistante"** in the portal when creating the deployment. The platform will:

1. Automatically provision a GCS bucket `cnp-{appName}-data` via Crossplane (wave 0)
2. Set the IAM binding so Cloud Run can read/write to it (wave 0)
3. Mount the bucket at `/data` inside your container via Cloud Run's native GCS volume mount (wave 1)
4. Set the env var `DATA_DIR=/data`

**You have nothing to do manually** — the bucket is created and configured as part of the onboarding flow, before the Cloud Run service is provisioned.

### Reading `DATA_DIR` in your app

```javascript
const DATA_DIR = process.env.DATA_DIR || '/tmp';   // /data on Cloud Run, /tmp locally
const DB_PATH  = path.join(DATA_DIR, 'myapp.db');

// Ensure the directory exists (needed locally; /data is pre-mounted on Cloud Run)
fs.mkdirSync(DATA_DIR, { recursive: true });

const db = new Database(DB_PATH);
```

### How persistence works

- GCS FUSE mounts the bucket at `/data` — reads and writes go directly to object storage
- SQLite writes are durably flushed to GCS on each transaction commit
- Data survives: container restarts, Cloud Run scale-to-zero, redeployments
- Cost: GCS Standard storage (~€0.02/GB/month for `europe-west9`)

> **Note:** GCS FUSE has higher latency than local disk (~10–100ms per write vs ~0.1ms). For high-throughput write workloads this matters; for a typical web app saving user events, it is negligible.

## 6. Environment variables injected by the platform

These env vars are always available inside your container on Cloud Run:

| Variable | Value | Description |
|----------|-------|-------------|
| `DATA_DIR` | `/data` (persistent) or `/tmp` (no storage) | Base directory for any file writes |
| `PORT` | `8080` | The port Cloud Run expects your HTTP server on |

Your app should always read `PORT` from the environment:

```javascript
const PORT = process.env.PORT || 8080;
app.listen(PORT, () => console.log(`Listening on :${PORT}`));
```

## 6b. Adding custom environment variables

If your app needs additional environment variables (API URLs, feature flags, configuration values, etc.), you **cannot set them yourself** — env vars for Cloud Run are declared in the platform's config-repo, which requires DevOps approval.

### How to request an env var

1. **After your deployment is created and onboarded**, contact your DevOps team and provide:
   - The variable name (e.g. `MY_API_URL`)
   - The value, or indicate that it is a secret (never send secret values over chat — DevOps will use the Secrets manager)
   - A brief explanation of what the variable is used for

2. The DevOps team will edit `config-repo/apps/{your-app}/crossplane/cloudrun-claim.yaml`, add the variable under `spec.forProvider.template.containers[0].env`, and submit a Manifest MR for manager approval.

3. Once approved and merged, the variable will be live in your Cloud Run service within ~2 minutes. Your DevOps contact will notify you.

### Reading env vars in your app

Always read configuration from `process.env` with a sensible local default:

```javascript
const apiUrl  = process.env.MY_API_URL  || 'http://localhost:4000';
const timeout = process.env.API_TIMEOUT || '5000';
const featureX = process.env.FEATURE_FLAG_X === 'true';
```

> **Never hardcode** URLs, timeouts, or feature flags directly in the source. Anything that differs between local development and production must come from the environment.

### Secret values

If you need an API key, password, or token, **do not** send the value over Slack or email. Tell your DevOps team it is a secret — they will provision it via the Secrets manager so it never appears in plain text in any config file.

## 7. Tests and linting

### Running lint locally

Always run lint before pushing — CI will fail if it doesn't pass locally:

```bash
npm run lint          # ESLint on src/
```

If you get `'describe' is not defined` or `'expect' is not defined`, you are missing `"jest": true` in your `.eslintrc.json` env (see below).

To lint your Dockerfile locally (requires Docker):

```bash
docker run --rm -i hadolint/hadolint < Dockerfile
```

---

### ESLint

A `.eslintrc.json` must exist at the repo root. Add `"jest": true` to `env` so ESLint knows about `describe`, `it`, and `expect`:

```json
{
  "env": { "node": true, "es2022": true, "jest": true },
  "parserOptions": { "ecmaVersion": 2022 },
  "rules": {
    "no-unused-vars": "error",
    "no-undef": "error"
  }
}
```

**Belt-and-suspenders:** also add `/* eslint-env jest */` as the first line of every `*.test.js` file. This makes the jest globals explicit in the file itself, and will never fail regardless of the root config:

```javascript
/* eslint-env jest */
const os = require('os');
process.env.DATA_DIR = os.tmpdir();
// ...
```

### Tests

Tests run with `npm test`. The test script must be defined in `package.json`:

```json
"scripts": {
  "test": "node --experimental-vm-modules node_modules/.bin/jest --ci --reporters=default --reporters=jest-junit"
}
```

**Required test dependencies:**

```json
"devDependencies": {
  "jest": "^29",
  "jest-junit": "^16",
  "supertest": "^6"
}
```

**Minimum tests required** (CI will fail without them):

```javascript
// Set DATA_DIR to a temp dir so tests don't touch /data
const os = require('os');
process.env.DATA_DIR = os.tmpdir();

const request = require('supertest');
const app = require('./index');

it('GET /healthz returns 200', async () => {
  const res = await request(app).get('/healthz');
  expect(res.status).toBe(200);
});

it('GET /ready returns 200', async () => {
  const res = await request(app).get('/ready');
  expect(res.status).toBe(200);
});
```

> **Important:** Always override `DATA_DIR` in tests so SQLite writes go to a temp directory, not `/data`.

### Jest config in `package.json`

```json
"jest": {
  "testEnvironment": "node"
},
"jest-junit": {
  "outputDirectory": ".",
  "outputName": "test-results.xml"
}
```

## 8. Secrets

| Secret | Where to set | Purpose |
|--------|-------------|---------|
| `CONFIG_REPO_TOKEN` | GitHub repo → Settings → Secrets and variables → Actions | Allows CI to push image tags to config-repo |

> The portal admin adds `CONFIG_REPO_TOKEN` to your repo during onboarding. You do not need to create it yourself.

Never commit secrets to your repository. The CI pipeline runs **Gitleaks** — any committed secret (API key, password, token) will fail the `scan-secrets` job and block the deployment.

## 9. Onboarding checklist

Use this before creating a deployment in the portal:

- [ ] App listens on a determined port
- [ ] `GET /healthz` returns `200 { "status": "ok" }`
- [ ] `GET /ready` returns `200 { "status": "ready" }`
- [ ] Dockerfile uses `FROM node:20-alpine` (both stages)
- [ ] Dockerfile has `USER 1000` (numeric, not `USER node`)
- [ ] Dockerfile has `EXPOSE {port}`
- [ ] Dockerfile uses `tini` as init process
- [ ] `.eslintrc.json` exists at repo root
- [ ] `npm test` passes locally
- [ ] Tests override `DATA_DIR` to `os.tmpdir()`
- [ ] No secrets committed to the repository
- [ ] If using persistent storage: check "DB persistante" in the portal — bucket and IAM are provisioned automatically by Crossplane

## 10. Common errors

### `scan-secrets` fails
A secret was found in the git history. Even if you deleted it in a later commit, Gitleaks scans the **full history**. You must rewrite history (`git filter-branch` or `git-filter-repo`) and rotate the leaked secret.

### `lint-hadolint` fails
- Check you're using `FROM node:20-alpine` (not `node:lts`, `node:latest`, `node:18-alpine`)
- Check `USER 1000` (not `USER node`, not missing entirely)
- Check `EXPOSE 8080` is present

### `test` fails
- Run `npm test` locally first
- Make sure `process.env.DATA_DIR = os.tmpdir()` is set at the top of the test file, before `require('./index')`
- Make sure `better-sqlite3` (or any native addon) is listed in `dependencies`, not `devDependencies`

### Cloud Run URL not appearing in portal
- The URL appears in the portal once Crossplane has finished provisioning the Cloud Run service (~1–3 minutes after a successful CI run)
- The portal polls automatically every 4 seconds and reloads when the URL is available
- If it never appears after 10 minutes: check `kubectl get v2service {appName} -o yaml` for errors in `status.conditions`

### App crashes on startup with `SQLITE_CANTOPEN`
Your app is trying to open the DB before the GCS volume is mounted, or `DATA_DIR` is not set. Make sure:
1. You read `process.env.DATA_DIR` (not a hardcoded path)
2. You call `fs.mkdirSync(DATA_DIR, { recursive: true })` before opening the DB
3. The onboarding completed successfully (check ArgoCD for the `{appName}-cloudrun` Application status)

### `update-cloudrun-claim` fails with push conflict
The retry loop (`for i in 1 2 3; do git pull --rebase && git push ...`) handles most concurrent push conflicts. If it still fails after 3 retries, it means multiple CI runs were updating config-repo simultaneously. Re-run the failed workflow.
