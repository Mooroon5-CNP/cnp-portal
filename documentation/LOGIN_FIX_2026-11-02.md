# Local admin login: bounded landing page — 2026-11-02

Reported symptom: local admin login on port 3001 keeps loading even with the
configured bootstrap password. Read-only inspection confirmed the local admin
exists, is active/approved, and its stored hash matches ADMIN_INITIAL_PASSWORD.
No password or database record was changed during this fix.

An in-memory HTTP regression using real Express, body parsing, bcrypt and sessions
confirms that valid local credentials return 302, renew the cookie and permit an
authenticated page. Invalid credentials return the existing error message.

A blocking path exists after successful login: GET / awaited Kubernetes, Datadog
and Argo via an unbounded Promise.all. In particular, the Kubernetes pod request
has no client timeout. A provider that never resolves could therefore leave the
landing page pending despite successful authentication.

The dashboard now bounds collection to three seconds, retains available data,
and renders unavailable counters as an em dash with an explicit source warning.
The deadline bounds the page response; it does not cancel underlying provider
operations. Existing service methods that swallow errors remain a separate
source-status limitation.

Regression: successful login followed by GET / with Kubernetes and Argo promises
that never resolve now returns 200 after the deadline and displays the warning.
The pending approval screen remains identical to main (last modified June 29).
GitHub login and admin credential logic are unchanged by this commit.

Validation: lint passed; 185 tests passed across 28 suites. Four existing
listener-dependent suites remain excluded due sandbox socket EPERM. The new
HTTP harness uses real Node request/response streams without TCP sockets.
Live browser confirmation remains required; the user's running service is not
reachable from this sandbox. Restart npm run dev:integration to load the fix.

## Subsequent launcher failure: SOURCE_TIMEOUT

The reported startup log showed an authenticated list_applications returning a
platform SOURCE_TIMEOUT after five seconds. The launcher treated any catalog error
as fatal and stopped both children before the portal could start.

The source-only catalog probe now permits degraded startup for SOURCE_TIMEOUT,
SOURCE_UNAVAILABLE, SOURCE_NOT_CONFIGURED and SOURCE_RESPONSE_INVALID. Identity,
authorization, protocol and unexpected errors remain fatal. The portal catalogue
endpoint and chat surface an actionable MCP_CATALOG_UNAVAILABLE message; no mock
fallback is introduced and future requests retry the real source.

Validation: lint and 19 targeted tests passed (startup policy, local login and
native adapters). Live source connectivity is still unverified: this fix prevents
an upstream outage from blocking the login page; it does not establish successful
GitHub registry access. GitHub OAuth and the approval screen are unchanged.
